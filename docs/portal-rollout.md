# Private admin and creator workspace rollout

The public storefront stays available without D1. The root Cloudflare Pages middleware and `_routes.json` run on `/admin/` and `/studio/`, validating Clerk's `__session` cookie and a D1 staff role before serving their static shells. Every private API validates a fresh bearer token and role again. No role can be granted from the website.

## Production setup

1. In Cloudflare, create a custom API token limited to the relevant account with **Pages Write** and **D1 Write**. Set a short expiry. Save it directly as the GitHub Actions repository secret `CLOUDFLARE_API_TOKEN`; never put it in source, workflow inputs, logs or chat. Find the account ID in Cloudflare; it is a non-secret workflow input.
2. A push of the workflow or setup script to `main` automatically runs **Configure My Little Project portal** in read-only `inspect` mode. You can also run it manually. It attempts to discover the Cloudflare account by matching the exact repository-backed Pages project; enter the account ID manually only if discovery is unavailable. The inspection reads project metadata and D1 database names/IDs. Check that Preview uses `mlp-workshop-dev`.
3. Run it again with mode `apply` and the same account ID. It creates or reuses `mlp-shop-production` (new databases use EU jurisdiction), applies `database/003_portal_workspace.sql`, binds `DB` in **Production** only, sets `fail_open=false` in both Production and Preview as Cloudflare requires, retries the current production deployment and checks `/api/shop`. It refuses to replace an unexpected production database. Its starter products remain hidden internal drafts; it creates no orders or payments.
4. Use the production Clerk instance for `mylittleproject.co.uk`. The development `pk_test_` instance stays on Preview. To set the four Production Pages variables, rerun `apply` with the optional production `pk_live_` publishable key and exact HTTPS issuer origin. The workflow derives the JWKS URL and allowed shop origin. These inputs are public client configuration, but they are stored in GitHub's workflow run metadata. No Clerk secret key belongs in source or the browser.
5. Sign in at `/account/`. Verify the production Clerk user ID directly in Clerk. The owner's account is an admin candidate. Configure the independent Cloudflare Access check in [admin-access-setup.md](admin-access-setup.md) before granting its `admin` role. Grant a separate, verified creator account the `creator` role from a trusted D1 operator console. The development user ID is not automatically a production user.
6. Verify anonymous redirects, wrong-role 403, Access-protected admin reads and writes, creator ownership, and public `/api/shop` response. Check that a public preview item is clearly labelled in development. Revoke the temporary Cloudflare token when setup and verification are complete.

The manual workflow never grants a staff role or enables checkout. It makes no changes in `inspect` mode. Its `apply` mode sends a narrow Pages PATCH for the production D1 binding, optional Clerk variables and fail-closed settings, then checks that existing production variable names and Preview's D1 binding and variables were preserved. Stop and inspect Cloudflare if any of those checks fail.

## Product bill of materials and sourcing

- Open an existing product in the Admin Desk's **Products** view. Its bill of materials has one editable row per part or material, including exact manufacturer and supplier part numbers, supplier HTTPS URL, pack quantity, quantity used per kit, buy price per pack including VAT, evidence type and note, date checked, availability, lead time, revision, sourcing stage and compatibility notes. Optional extras and alternatives are tagged separately from core kit parts.
- Flight Radar has an **Open Flight Radar BOM** shortcut and a one-click starter requirements list. The starter rows are deliberately unpriced and specify the ESP32-S3 Zero, a GC9A01 pin-header display, KY-040 module, jumpers, USB cable and enclosure. Verify the correct variant, connector, stock and supplier for each before entering a price; the starter button does not invent a supplier or approve a part.
- The private cost summary allocates a sourced pack price by `ceil(price in pence × quantity used per kit ÷ units in pack)` for each core row. It shows coverage, partial subtotal, unpriced/estimated core parts, parts not approved and stock gaps. This is an approximate per-kit allocation; it does not include shipping, packaging, assembly, payment fees or returns. A price counts as sourced only with a supplier, check date and HTTPS listing or a specific source note. An estimate may be stored but is excluded from the sourced subtotal.
- The same BOM figures and source entries are included in the downloadable private launch snapshot for weekly reviews. BOM changes appear in the Admin Desk activity feed. The `/api/admin/bom` mutations and private workspace read require both the Admin Clerk role and the independently signed Cloudflare Access proof. The table is created after authorised access, with its reviewed migration in `database/007_product_bom.sql`. Neither `/api/shop` nor `/api/workshop` expose supplier prices or the BOM; product previews and checkout remain unaffected.

## Product and part photographs

- Open a saved product in **Admin Desk → Products**. The **Final product photo** panel accepts an image from the owner's device, a meaningful alt description and optional caption. The browser converts it to a compact JPEG, removing camera metadata; the server accepts up to 400 KB and checks the file's actual image signature. A product photo is private by default. Selecting **Show this real photo on the public product preview** publishes it only while the product itself is set to **Public preview**. Removing or unpublishing the photo restores the concept illustration. The public catalogue API exposes only the selected photo URL and description for visible products; the binary route checks visibility on every request.
- Each saved BOM part has a private photograph field in its edit form and thumbnail in its sourcing card. The part image cannot be published via this interface and is returned only by the separately protected Admin Desk media API. Removing a BOM row also removes its image. Photo changes appear in the activity feed and product/part photo coverage appears in the downloadable launch snapshot. The idempotent schema is in `database/008_product_media.sql`; an authorised Admin Desk read creates it in an existing database.
- One compact image is stored per product or part in D1 for the early catalogue. Keep originals outside the site. For a larger library or multiple high-resolution views, migrate the binaries to object storage while preserving the private/public visibility checks. A photograph of a current prototype is evidence of that prototype, not proof of final contents or a completed safety review. No kit has been photographed or published by this change.
